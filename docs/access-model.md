# Модель доступа к парку

Узлы парка стоят в изолированной сети `labnet` (10.10.10.0/24) за NAT: маршрута из домашней сети в эту подсеть нет. Здесь описано, через какую точку рабочая машина попадает на узлы, как она их адресует и как проверяет, что попала туда, куда шла.

## Бастион — гипервизор

Единственная точка входа по SSH в сегмент — гипервизор (SSH-алиас `lab`). Он видит узлы через виртуальный мост `virbr-lab`, поэтому с рабочей машины на любой узел парка ходим через него с помощью `ProxyJump` — по имени из зоны `lab.internal` или по адресу. Почему в `authorized_keys` узлов лежит ключ рабочей машины, а не гипервизора, — в [инструкции по развёртыванию](deploy/README.md).

План проекта называл бастионом узел `mgmt`. От этого варианта отказались по двум причинам:

- `mgmt` стоит за тем же NAT, и путь к нему всё равно идёт через гипервизор. Бастион на `mgmt` не убирает гипервизор с пути, а добавляет второй прыжок: архитектура сложнее, выгоды нет.
- Упади `mgmt` — пропал бы доступ к узлам, которые без него продолжают работать. Гипервизор такого отказа не добавляет: без него не работает и сам парк.

```text
Отклонено:  [Mac] ──> [Dell (lab)] ──> [ВМ mgmt] ──> [ВМ web]    двойной прыжок
Принято:    [Mac] ──> [Dell (lab)] ─────────────────> [ВМ web]    один прыжок
```

За `mgmt` остаются внутренний DNS и, в проекте 02, стек мониторинга.

### Компромисс

В продакшене гипервизор — «царь-машина»: SSH к нему означает доступ к памяти, дискам и консолям всех виртуальных машин. Поэтому гипервизоры прячут в изолированную служебную сеть (management VLAN), а инженеры ходят через отдельный минимальный бастион без сервисов. Здесь весь парк живёт на одном физическом ноутбуке, и отдельная ВМ только ради прыжка избыточна: гипервизор в роли бастиона — осознанный компромисс между удобством и сложностью.

## Настройка рабочей машины

`~/.ssh/config`:

```sshconfig
# Гипервизор — бастион
Host lab
    HostName <IP_гипервизора_в_LAN>
    User <пользователь_гипервизора>
    IdentityFile ~/.ssh/homelab_ed25519

# Узлы парка — по адресу и по имени, через бастион
Host 10.10.10.* *.lab.internal
    User devops
    UserKnownHostsFile ~/.ssh/known_hosts_lab
    StrictHostKeyChecking accept-new
    IdentityFile ~/.ssh/homelab_ed25519
    ProxyJump lab
```

Адреса и имена описаны одним блоком. Шаблон `Host` сопоставляется со строкой, набранной в командной строке, до всякого DNS-запроса: клиент не знает, что за `web.lab.internal` стоит `10.10.10.10`, и шаблон `10.10.10.*` имя не поймает. Два блока с одинаковым набором настроек со временем разъедутся, поэтому шаблоны перечислены через пробел в одной строке `Host`.

Блоки при этом не выбираются по одному: клиент применяет все подошедшие, и для каждого параметра действует первое встреченное значение. Поэтому общий `Host *`, если он появится, ставится в конец файла.

Какие настройки клиент на самом деле применит к имени, видно без подключения:

```bash
ssh -G web.lab.internal | grep -E '^(user|proxyjump|userknownhostsfile|identityfile)'
```

```text
user devops
identityfile ~/.ssh/homelab_ed25519
userknownhostsfile /Users/<user>/.ssh/known_hosts_lab
proxyjump lab
```

## Имена разрешает бастион

Рабочая машина зону `lab.internal` не знает, и знать ей не нужно: при `ProxyJump` имя цели разрешает бастион. Гипервизор отправляет запросы зоны на dnsmasq узла `mgmt` — как это устроено, описано в [этапе 05](deploy/05-internal-dns.md).

На рабочей машине имя не разрешается:

```bash
ping -c1 web.lab.internal
```

```text
ping: cannot resolve web.lab.internal: Unknown host
```

А вход по имени работает на всех узлах парка — по ключу, без пароля:

```bash
for h in web app mgmt; do ssh "$h.lab.internal" 'hostname; hostname -I'; done
```

```text
web
10.10.10.10
app
10.10.10.20
mgmt
10.10.10.30
```

## Когда DNS парка лежит

Зону `lab.internal` обслуживает один узел — `mgmt`, второго сервера с зоной нет. Поэтому отказ `dnsmasq` на `mgmt` лишает имён весь парк: бастион не разрешает имена узлов, а сами узлы не разрешают вообще ничего — `10.10.10.30` у них единственный резолвер. Почему второй сервер без зоны в списке резолверов — не резерв, а ловушка, разобрано в [этапе 05](deploy/05-internal-dns.md#mgmt-отчуждение-сетевого-конфига-у-cloud-init). Внешние имена самого гипервизора от `mgmt` не зависят: туда гипервизор отправляет только запросы зон парка — прямой и обратной.

**Сигнатура.** Вход по имени с рабочей машины падает так:

```text
channel 0: open failed: connect failed: Name or service not known
stdio forwarding failed
Connection closed by UNKNOWN port 65535
```

Текст сбивает с толку: «name not known» читается как опечатка в имени, но имя верное — его не смог разрешить бастион. Канал до узла открывает `sshd` на гипервизоре, и ту же ошибку он пишет в журнал. Искать её нужно по имени программы, а не по юниту: строку пишет дочерний процесс сессии, и фильтр `-u ssh` её не покажет.

```bash
sudo journalctl -t sshd --since "30 min ago" --no-pager
```

```text
sshd[…]: error: connect_to web.lab.internal: unknown host (Name or service not known)
```

**Причину проверяем, спрашивая сервер напрямую.** На гипервизоре:

```bash
resolvectl query --cache=no app.lab.internal   # зона: resolve call failed ... Connection refused
resolvectl query --cache=no github.com         # внешние имена: ответ через LAN-интерфейс
```

`Connection refused` по зоне при живых внешних именах означает, что `mgmt` в сети, но на `10.10.10.30:53` никто не слушает. Дальше — на самом `mgmt`:

```bash
sudo systemctl status dnsmasq --no-pager -n 5
sudo ss -tulpn 'sport = :53'
```

**Запасной путь — по адресу.** Блок `Host 10.10.10.* *.lab.internal` описывает и адреса, а адрес бастиону разрешать не нужно, поэтому при лежащем DNS вход по адресу работает — в захвате на `virbr-lab` при таком входе нет ни одного DNS-пакета:

```bash
ssh 10.10.10.10 true
```

По адресу же DNS и восстанавливают: конфиг доставляется на `10.10.10.30` из репозитория — [этап 05](deploy/05-internal-dns.md#установка-и-настройка-dnsmasq).

## Доверие ключам узлов

`known_hosts` хранит ключ узла под именем, к которому шло подключение: `10.10.10.30` и `mgmt.lab.internal` для клиента — две разные записи, даже если за ними одна машина. Первое подключение по имени — новый хост, и `StrictHostKeyChecking accept-new` принимает его ключ без вопроса:

```text
Warning: Permanently added 'mgmt.lab.internal' (ED25519) to the list of known hosts.
```

Поэтому после первого входа по имени отпечаток сверяется с уже известным по адресу:

```bash
ssh-keygen -lF mgmt.lab.internal -f ~/.ssh/known_hosts_lab
ssh-keygen -lF 10.10.10.30       -f ~/.ssh/known_hosts_lab
```

```text
mgmt.lab.internal ED25519 SHA256:hHKLKJq3/ZI9/BWmjpJy+4IApPkitA7zjOCdmtRjhQ0
10.10.10.30 ED25519 SHA256:hHKLKJq3/ZI9/BWmjpJy+4IApPkitA7zjOCdmtRjhQ0
```

Отпечатки совпадают: по имени отвечает та же машина, что и по адресу, — узел не подменён, запись зоны верна.

### Отдельный known_hosts для узлов парка

Узлы парка пересоздаются из шаблона: новый узел получает прежние адрес и имя, но новые host-ключи, и клиент встречает его предупреждением `REMOTE HOST IDENTIFICATION HAS CHANGED`. Поэтому для парка заведён отдельный файл известных хостов (`UserKnownHostsFile ~/.ssh/known_hosts_lab` в блоке выше): лабораторный шум не смешивается с основным `~/.ssh/known_hosts`. У пересозданного узла устаревают обе его записи — под адресом и под именем.
