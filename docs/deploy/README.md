# Как воспроизвести

Развёртывание автоматизировано: инфраструктура поднимается по этапам, без ручной настройки каждой ВМ. Порядок этапов не произвольный — сеть нужна образу, образ нужен узлам, узлы нужны внутреннему DNS.

## Требования

- настроено SSH-соединение с рабочей машины до узла-гипервизора (вход по ключу);
- публичный ключ рабочей машины лежит на гипервизоре **отдельным файлом** — по умолчанию `~/.ssh/client_mac_key.pub`;
- на узле-гипервизоре развёрнута Ubuntu Server 24.04;
- узел поддерживает аппаратную виртуализацию — проверяем:

```bash
egrep -c '(vmx|svm)' /proc/cpuinfo   # результат > 0 — поддержка есть
```

Про второй пункт: этот файл — не то же самое, что настроенный вход на гипервизор. Ключ из него cloud-init кладёт в `authorized_keys` каждого узла парка, и это должен быть ключ **рабочей машины**, а не гипервизора. Причина в том, как работает ProxyJump: гипервизор не «перекидывает» пользователя дальше своей сессией, он лишь прокидывает TCP-соединение, а SSH-сессию с узлом парка устанавливает и аутентифицирует сам клиент, сквозь этот туннель. Положишь в шаблон ключ гипервизора — с рабочей машины на узлы не зайдёшь.

## Склонировать репозиторий на узел-гипервизор

```bash
mkdir -p ~/lab_projects && cd ~/lab_projects
git clone https://github.com/ArtemKravets/infra_foundation.git
cd infra_foundation
```

Дальнейшие команды выполняются из этого каталога или ссылаются на него по пути `~/lab_projects/infra_foundation`.

## Проверка парка одной командой

[`scripts/verify-park.sh`](../../scripts/verify-park.sh) — приёмочная проверка парка: один запуск с рабочей машины отвечает, совпадает ли парк с планом. Запускать её стоит после развёртывания парка (этап 5) и после любого изменения в нём.

| Где | Проверка | Ожидание |
| --- | --- | --- |
| гипервизор | `virsh domstate` для web, app, mgmt | `running` |
| каждый узел | вход по SSH | ключом, без интерактивных вопросов |
| каждый узел | глобальный IPv4 | адрес из [плана адресации](../addressing.md) |
| каждый узел | `dig app.lab.internal @10.10.10.30` | `10.10.10.20` |
| каждый узел | `ping -c1 web.lab.internal` | ответ получен |

Скрипт запускается на рабочей машине, настроенной по [модели доступа](../access-model.md): алиас `lab` для гипервизора и блок `Host 10.10.10.* *.lab.internal` с `ProxyJump lab`. Совместим с bash 3.2 — системным bash macOS. Из корня клона репозитория:

```bash
bash scripts/verify-park.sh; echo "exit code: $?"
```

```text
=== 1. Гипервизор (lab): состояние ВМ ===
[OK]   vm/web: state is running
[OK]   vm/app: state is running
[OK]   vm/mgmt: state is running

=== 2. Узлы парка: SSH, IPv4, DNS (dig), связность (ping) ===
[OK]   web.lab.internal [ssh]: вход по ключу
[OK]   web.lab.internal [ip]: глобальный IPv4 10.10.10.10
[OK]   web.lab.internal [dig]: app.lab.internal @10.10.10.30 -> 10.10.10.20
[OK]   web.lab.internal [ping]: web.lab.internal доступен (1 packet received)
...
Итог: OK=15, FAIL=0 (всего проверок: 15)
exit code: 0
```

- Код выхода `0` — всё сходится с планом, `1` — хотя бы одна проверка не прошла.
- Провал одной проверки не обрывает прогон. Если на узел не пустило по SSH, его остальные проверки отчитываются строками «не выполнено», поэтому в отчёте всегда 15 проверок.
- Прогон не виснет на недоступном узле и не ждёт ввода: `BatchMode=yes`, `ConnectTimeout=5`, `ping -W2`, `dig +time=2 +tries=1`. Полный прогон занимает 17–19 с: каждая проверка на узле — отдельный вход через бастион.

Строка FAIL несёт код возврата и stderr команды, а не догадку о причине. `dig @10.10.10.30` спрашивает dnsmasq напрямую, в обход резолвера узла, а `ping web.lab.internal` идёт штатным путём узла — через его резолвер — и проверяет связность. Поэтому отчёт сразу указывает на звено:

| Что в отчёте | Где искать |
| --- | --- |
| `[ssh]` FAIL, `exit=255: … Name or service not known` | бастион не разрешил имя: узла нет в зоне или лежит DNS парка — [запасной путь](../access-model.md#когда-dns-парка-лежит) |
| `[ssh]` FAIL, `exit=255: … No route to host` | имя разрешилось, узел не ответил |
| `[dig]` FAIL | сервер зоны — dnsmasq на `mgmt` |
| `[dig]` OK, `[ping]` FAIL `exit=1` | имя разрешилось, ответа нет — цель или сеть до неё |
| `[dig]` OK, `[ping]` FAIL `exit=2` | ошибка до отправки пакета, например имя не разрешилось: сервер зоны отвечает — смотреть резолвер узла |
