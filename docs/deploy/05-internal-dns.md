# Этап 5. Парк и внутреннее разрешение имён

До этого шага узлы парка знают друг друга только по адресам из [`docs/addressing.md`](../addressing.md). Здесь на `mgmt` поднимается `dnsmasq` — служба, которая отвечает на запросы имён зоны `lab.internal` (`app.lab.internal` → `10.10.10.20`), а всё, что к зоне не относится, пересылает вышестоящему серверу — шлюзу сети libvirt `10.10.10.1`. Это первый инфраструктурный сервис парка: до сих пор `mgmt` был просто виртуальной машиной с доступом по SSH.

Сначала настраивается серверная сторона — «кто отвечает на запросы»; проверки этой части адресуют сервер явно: `dig ... @10.10.10.30`. Затем из шаблона поднимаются оставшиеся узлы парка, и в конце этапа доводится клиентская сторона — «у кого узлы спрашивают».

## Почему собственный dnsmasq на mgmt, а не записи в libvirt

На гипервизоре уже работает экземпляр `dnsmasq`, поднятый libvirt для сети `labnet` — он раздаёт адреса из DHCP-пула. Логичный вопрос: почему не прописать имена узлов туда?

* **Конфликт управления.** Конфигурацию того экземпляра генерирует сам libvirt из XML-описания сети. Правки, внесённые руками, теряются при следующем перезапуске сети: libvirt пересобирает конфиг заново. К тому же имена там привязаны к DHCP-арендам, а узлы парка адресуются статически.
* **Разделение ролей и радиус поражения.** Инфраструктурные службы (DNS, позже — мониторинг и сбор логов) должны жить внутри инфраструктуры, а не на хосте, который её запускает. Ошибка в конфиге `dnsmasq` на `mgmt` ломает только разрешение имён; ошибка в конфигурации libvirt останавливает весь парк.
* **Портативность.** Парк, перенесённый на другой гипервизор или в облако, потеряет встроенный DNS вместе с libvirt. Узел `mgmt` переезжает вместе со своими службами и продолжает работать в любой среде.

## Конфликт за 53-й порт и его развязка

DNS слушает 53-й порт (UDP и TCP). В Ubuntu этот порт уже частично занят: в системе работает `systemd-resolved` — локальный кеширующий резолвер, который принимает запросы программ узла на адресе `127.0.0.53` и пересылает их вышестоящим DNS-серверам, полученным из настроек сетевого интерфейса. Именно на этот адрес указывает `/etc/resolv.conf`.

`dnsmasq` при старте по умолчанию пытается занять 53-й порт на **всех** адресах узла сразу — это называется привязкой к wildcard-адресу `0.0.0.0`. В этот набор попадает и `127.0.0.53`, уже занятый резолвером, поэтому служба падает с ошибкой `failed to create listening socket for port 53: Address already in use`.

Развязок две, обе рабочие.

**Вариант А — узкий бинд (выбран).** Явно перечисляем адреса, на которых служба должна слушать (`listen-address`), и требуем привязываться строго к ним, а не к wildcard (`bind-interfaces`). `dnsmasq` садится на `10.10.10.30:53` и `127.0.0.1:53`, `systemd-resolved` остаётся на `127.0.0.53:53` — это разные адреса, конфликта нет.

**Вариант Б — освободить порт.** Отключить у `systemd-resolved` заглушку-слушатель (`DNSStubListener=no`) и переназначить `/etc/resolv.conf` на `dnsmasq`. Так делают, например, при установке Pi-hole. Вариант законный, но он уводит с штатной схемы Ubuntu и требует вручную закреплять `/etc/resolv.conf`, который иначе будет переписан.

**Почему выбран вариант А:**

* **Меньше вмешательства.** Штатный резолвер Ubuntu остаётся нетронутым; на узле не появляется настройки, которую придётся объяснять и поддерживать отдельно.
* **Предсказуемость.** Служба слушает только там, где ей явно разрешили. Если позже на `mgmt` появятся новые интерфейсы (сети контейнеров, VPN), `dnsmasq` не начнёт молча обрабатывать запросы на их адресах.
* **Унификация.** Сетевая настройка `mgmt` остаётся такой же, как у `web` и `app`: не нужно помнить, что один узел парка сконфигурирован особым образом.

## Развёртывание узла mgmt

**Почему при создании узла DNS указывается вручную.** При первой загрузке `cloud-init` устанавливает `qemu-guest-agent`, а для этого пакетному менеджеру нужно разрешить имя `archive.ubuntu.com`. По умолчанию скрипт развёртывания прописывает узлу DNS `10.10.10.30`, то есть самого себя, — но `dnsmasq` на `mgmt` в этот момент ещё не установлен, и установка агента упадёт на разрешении имени. Поэтому при развёртывании передаём адрес DNS явно: `10.10.10.1` — шлюз сети libvirt, где работает её собственный `dnsmasq`.

Разворачиваем узел, передавая на вход его адрес, адрес DNS и 2048 МБ оперативной памяти (объём под управляющий узел заложен в бюджете ОЗУ гипервизора):

```bash
./scripts/provision-node.sh mgmt --ip 10.10.10.30 --dns 10.10.10.1 --ram 2048
```

Скрипт отработал — проверяем, что домен зарегистрирован в libvirt:

```bash
virsh list --all

# Ожидаем увидеть узел mgmt в состоянии running
```

Подключаемся к `mgmt` по SSH с рабочей машины и выполняем проверки на самом узле:

```bash
# Статический адрес закреплён за интерфейсом
# Ожидаем интерфейс в состоянии UP с адресом 10.10.10.30
ip -4 addr show

# Маршрут по умолчанию
# Ожидаем шлюз 10.10.10.1
ip route

# Связность с внешней сетью через NAT гипервизора
# Ожидаем 0% packet loss
ping -c1 8.8.8.8

# Разрешение имён работает через указанный DNS-сервер
# Ожидаем непустой ответ с адресом
resolvectl query archive.ubuntu.com

# Домен поиска назначен интерфейсу
# Ожидаем lab.internal
resolvectl domain
```

Проверки на стороне гипервизора:

```bash
# Узел не брал адрес из DHCP-пула: адресация статическая
# В таблице аренд узла mgmt быть не должно
virsh net-dhcp-leases labnet

# qemu-guest-agent установился и отвечает гипервизору
# Должны увидеть интерфейсы узла mgmt
virsh domifaddr mgmt --source agent
```

## Установка и настройка dnsmasq

**Установка.** Обновляем списки пакетов и ставим службу:

```bash
sudo apt update
sudo apt install -y dnsmasq
```

Сразу после распаковки пакет пытается запустить службу с конфигурацией по умолчанию — то есть с привязкой к `0.0.0.0:53`, где уже сидит `systemd-resolved`. Установка завершается сообщением о неудачном старте `dnsmasq.service`. Это ожидаемо и не является поломкой: конфигурацию мы задаём следующим шагом.

**Конфигурация**. Основной файл `/etc/dnsmasq.conf` править не нужно: при запуске службы `dnsmasq` получает флаг, которым подключает файлы из каталога `/etc/dnsmasq.d`. Не читаются оттуда только файлы с суффиксами `.dpkg-dist`, `.dpkg-old`, `.dpkg-new`. Отсюда неочевидное следствие: резервная копия вида `lab.conf.bak`, оставленная в этом каталоге, тоже будет прочитана — директивы удвоятся, а ошибка получится трудноуловимой. Бэкапы держим вне `/etc/dnsmasq.d`.

Готовый конфиг лежит в репозитории: [`configs/dnsmasq/lab.conf`](../../configs/dnsmasq/lab.conf). Его нужно доставить на узел `mgmt` в каталог `/etc/dnsmasq.d/`. На узлах парка авторизован только публичный ключ рабочей машины, поэтому гипервизор, где лежит репозиторий, напрямую до узла не дотянется: копируем конфиг сначала на рабочую машину, а оттуда — на `mgmt` через ProxyJump.

```bash
# На домашней машине копируем с гипервизора конфиг
cd ~
rsync lab:~/infra_foundation/configs/dnsmasq/lab.conf .

# Отправляем конфиг на узел `mgmt`
rsync --rsync-path="sudo rsync" lab.conf devops@10.10.10.30:/etc/dnsmasq.d/
```

Что задаёт конфиг (подробные комментарии — в самом файле):

* адреса прослушивания и жёсткую привязку к ним — развязка конфликта из раздела [«Конфликт за 53-й порт»](#конфликт-за-53-й-порт-и-его-развязка);
* вышестоящий DNS-сервер `10.10.10.1`, заданный явно, и запрет читать `/etc/resolv.conf`: без этого запроса узла ушли бы по кругу, когда клиентская сторона будет переключена на `10.10.10.30`;
* зону `lab.internal` — она обслуживается только локально и наружу не пересылается;
* статические записи узлов парка (прямые и обратные) по таблице из [`docs/addressing.md`](../addressing.md).

В конфиге намеренно **нет** директивы `dhcp-range`: без неё `dnsmasq` работает только как DNS. Второй DHCP-сервер в сегменте, где адреса уже раздаёт libvirt, сломал бы адресацию парка.

**Проверка синтаксиса.** Перед запуском службы проверяем конфигурацию утилитой самого демона:

```bash
dnsmasq --test

# Ожидаем: dnsmasq: syntax check OK.
```

**Запуск и автозагрузка:**

```bash
sudo systemctl restart dnsmasq
sudo systemctl enable dnsmasq

# Ожидаем: active и enabled
systemctl is-active dnsmasq
systemctl is-enabled dnsmasq
```

## Проверки

**1. Сетевые сокеты (UDP и TCP на 53-м порту)**

```bash
sudo ss -lntup 'sport = :53'
```

Что должно быть в выводе:

* процесс `dnsmasq` — **строго** на `127.0.0.1:53` и `10.10.10.30:53`, по две строки на адрес (UDP и TCP);
* процесс `systemd-resolve` — на `127.0.0.53:53`, на месте и работоспособен;
* строк с `0.0.0.0:53` быть не должно.

**2. Прямые записи зоны `lab.internal`**

Обращаемся напрямую к новому серверу (`@10.10.10.30`):

```bash
dig +short web.lab.internal @10.10.10.30
dig +short app.lab.internal @10.10.10.30
dig +short mgmt.lab.internal @10.10.10.30

# Ожидаемый вывод:
# 10.10.10.10
# 10.10.10.20
# 10.10.10.30
```

**3. Обратная зона (PTR-запись)**

Флаг `-x` выполняет обратный запрос — поиск имени по адресу:

```bash
dig +short -x 10.10.10.20 @10.10.10.30

# Ожидаемый вывод: app.lab.internal.
```

**4. Изоляция зоны (NXDOMAIN)**

Убеждаемся, что несуществующие имена внутри `lab.internal` не уходят во внешнюю сеть:

```bash
dig nosuch.lab.internal @10.10.10.30
```

В заголовке ответа (`->>HEADER<<-`) статус должен быть строго `status: NXDOMAIN`. Ответ пришёл от нашего сервера, а запрос наружу не отправлялся.

**5. Пересылка внешних запросов**

Убеждаемся, что имена за пределами зоны разрешаются через вышестоящий сервер `10.10.10.1`:

```bash
dig +short ya.ru @10.10.10.30

# Ожидаемый вывод: публичные адреса домена
```

**6. Служба переживает перезагрузку узла**

Жёсткая привязка к адресу (`bind-interfaces`) означает, что на старте службе нужен уже сконфигурированный интерфейс. Проверяем, что порядок запуска при загрузке соблюдается:

```bash
sudo reboot

# После подъёма узла:
systemctl is-active dnsmasq
dig +short app.lab.internal @10.10.10.30
```

Служба в состоянии `failed` сразу после загрузки (при том, что вручную она запускается нормально) — признак того, что `dnsmasq` стартовал раньше, чем на интерфейсе появился адрес `10.10.10.30`.


## Развёртывание узлов web и app

Серверная сторона зоны работает — и с этого момента становится верным умолчание скрипта развёртывания. Для `mgmt` адрес DNS приходилось передавать вручную, обходя курицу и яйцо; теперь `dnsmasq` на `10.10.10.30` жив, и узлы рождаются с правильным резолвером по умолчанию. Адрес резолвера и поисковый домен попадают в netplan узла через `network-config`, то есть клиентская сторона у `web` и `app` настраивается самим фактом развёртывания и отдельного шага не требует.

```bash
./scripts/provision-node.sh web --ip 10.10.10.10
./scripts/provision-node.sh app --ip 10.10.10.20 --ram 2048
```

`web` идёт с параметрами по умолчанию — 1024 МБ по бюджету ОЗУ гипервизора. `app` получает 2048 МБ: он понесёт PostgreSQL вместе с Gitea. Диски обоим оставлены дефолтными — том под данные `app` добавляется отдельным блочным устройством на этапе установки базы, а не нарезается внутри системного диска.

Проверки на гипервизоре:

```bash
virsh list --all                       # web, app, mgmt — все в состоянии running
virsh domifaddr web --source agent     # 10.10.10.10
virsh domifaddr app --source agent     # 10.10.10.20
virsh net-dhcp-leases labnet           # таблица пуста: весь парк адресуется статически
```

Ответ гостевого агента доказывает здесь больше, чем адрес: агент ставится на первой загрузке через apt, а значит узел успешно разрешил `archive.ubuntu.com` — через `mgmt`.

Проверки на каждом из узлов:

```bash
resolvectl status | grep -A2 'Current DNS'   # 10.10.10.30
resolvectl domain                            # lab.internal
resolvectl query mgmt.lab.internal           # 10.10.10.30, уже без явного @
ping -c1 8.8.8.8                             # NAT гипервизора на месте
```

`resolvectl` здесь вместо `dig` намеренно: он часть systemd и есть в образе из коробки, тогда как `dig` приезжает с пакетом `dnsutils`, которого на свежем узле может не быть.

## Клиентская сторона: mgmt и гипервизор

`web` и `app` получили резолвер при рождении. Незакрытыми остаются две машины, и механизмы для них нужны разные.

### mgmt: отчуждение сетевого конфига у cloud-init

`mgmt` родился с `--dns 10.10.10.1` и остаётся единственным узлом парка, который не разрешает имена зоны, которую сам же обслуживает. Резолвер нужно заменить на `10.10.10.30`, то есть на него самого.

**Почему это не решается drop-in файлом netplan.** Netplan читает `/etc/netplan/` в лексикографическом порядке, и для скалярных значений побеждает более поздний файл. Со списками он поступает иначе: `nameservers.addresses` и `search` не заменяются, а склеиваются. Дописав свой файл с `10.10.10.30`, вы получите на интерфейсе два сервера — `10.10.10.1` и `10.10.10.30`, — а директивы удаления элемента из ранее объявленного списка в синтаксисе netplan нет. Номер файла меняет порядок адресов, но не состав.

**Почему два сервера в списке — не резервирование, а ловушка.** Список DNS-серверов страхует `systemd-resolved` от недоступного сервера, но не от неверного ответа. Если `dnsmasq` на `mgmt` перезапускается или падает, резолвер уходит по таймауту на `10.10.10.1` — а шлюз сети libvirt про зону `lab.internal` ничего не знает и отвечает NXDOMAIN. Это валидный окончательный ответ: `resolved` его принимает, кэширует и фиксирует текущий сервер. Узел, который сам является источником правды для зоны, начинает утверждать, что зоны не существует, — и способен остаться в этом состоянии после того, как `dnsmasq` поднимется. Плавающее поведение такого рода диагностируется тяжело именно потому, что ответ приходит уверенный.

Рабочий путь — забрать управление сетью у `cloud-init` и оставить на узле один сетевой файл с единственным резолвером. Свою задачу, первичную инициализацию узла, `cloud-init` уже выполнил; дальше сетью управляет администратор.

```bash
# cloud-init больше не генерирует netplan на этом узле
echo 'network: {config: disabled}' | sudo tee /etc/cloud/cloud.cfg.d/99-disable-network-config.cfg

# даём сетевому файлу честное имя: cloud-init им больше не владеет
sudo mv /etc/netplan/50-cloud-init.yaml /etc/netplan/50-lab-net.yaml
```

В `/etc/netplan/50-lab-net.yaml` секция `nameservers` приводится к единственному серверу:

```yaml
nameservers:
    addresses:
        - 10.10.10.30
    search:
        - lab.internal
```

Остальные поля — адрес, маршрут, `match` — не трогаем. Права файла должны остаться `600`: netplan предупреждает о конфигурации, доступной на чтение другим пользователям.

```bash
sudo netplan apply
sudo reboot
```

Перезагрузка здесь не формальность: она подтверждает, что `cloud-init` действительно не вернул свой файл при старте.

### Гипервизор: маршрутизация одной зоны

Гипервизор — не узел парка. Его собственный резолвер приходит от домашнего роутера, и через него идёт весь внешний трафик хоста; подменять этот резолвер на `mgmt` нельзя, иначе хост, который запускает парк, начнёт зависеть от собственной виртуальной машины в вопросе выхода в интернет.

При этом зона нужна ему не для удобства. `ProxyJump` разворачивается в `ssh -W <имя>:22 <бастион>`, то есть имя цели разрешает джамп-хост, а не клиент. Пока гипервизор не знает `lab.internal`, подключение к узлам парка по именам с рабочей машины не заработает ни при каких настройках клиента.

Нужное здесь называется routing-only domain — правило «запросы этой зоны отправляй этому серверу, всё остальное оставь как есть». В `systemd-resolved` такой домен записывается с префиксом `~`. Готовый конфиг лежит в репозитории: [`configs/host/resolved.conf.d/lab.conf`](../../configs/host/resolved.conf.d/lab.conf).

```bash
sudo mkdir -p /etc/systemd/resolved.conf.d
sudo install -m 644 configs/host/resolved.conf.d/lab.conf /etc/systemd/resolved.conf.d/lab.conf
sudo systemctl restart systemd-resolved
```

Что задают две строки конфига:

* `DNS=10.10.10.30` — сервер, знающий зону;
* `Domains=~lab.internal` — маршрутизируемый домен. Тильда несёт здесь весь смысл. Без неё запись стала бы поисковым доменом, и хост начал бы дописывать `.lab.internal` к каждому короткому имени. С тильдой она не дописывается никуда и работает только как маршрут: зона уходит на `10.10.10.30`, всё прочее продолжает идти через LAN-интерфейс.

Права `644`, а не `600`: служба работает под непривилегированным пользователем — `systemctl show systemd-resolved -p User` показывает `systemd-resolve`, — поэтому файл должен быть читаем не только владельцем. Секретов в нём нет.

Привязать настройку к интерфейсу `virbr-lab` было бы логичнее по смыслу, раз зона достижима именно через него. Но `virbr-lab` создаёт и пересоздаёт libvirt при перезапуске сети, netplan им не управляет, и настройка, повешенная на такой линк, не переживает ни перезапуска сети, ни перезагрузки хоста. Поэтому — глобальный маршрутизируемый домен.

### Проверки клиентской стороны

На `mgmt` после перезагрузки:

```bash
ls -l /etc/netplan/                          # единственный файл, права -rw-------
resolvectl status | grep -A2 'DNS Servers'   # ровно один сервер: 10.10.10.30
resolvectl query web                         # 10.10.10.10: короткое имя дополнено поисковым доменом
resolvectl query ya.ru                       # внешние имена по-прежнему разрешаются
```

На гипервизоре:

```bash
resolvectl status                  # Global: DNS 10.10.10.30, Domains ~lab.internal;
                                   # LAN-интерфейс сохраняет свой DNS от роутера
resolvectl query app.lab.internal  # 10.10.10.20
resolvectl query ya.ru             # уходит через LAN-интерфейс, а не через парк
ping -c1 web.lab.internal
```

Связность по именам внутри парка — с любого узла:

```bash
ping -c1 app.lab.internal
```
