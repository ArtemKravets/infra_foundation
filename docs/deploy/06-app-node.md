# Этап 6. Узел app: данные, база и сервис

Узел `app` несёт рабочую нагрузку парка — Gitea поверх PostgreSQL. Прежде чем ставить службы, узел получает отдельный диск под данные: системный диск остаётся за ОС, а база и репозитории живут на своих томах.

## Почему данные на отдельном диске

* **Система отдельно от данных.** Узел можно чинить и пересоздавать, не трогая данные, а разросшиеся репозитории не забьют корневой раздел и не уронят ОС.
* **Два тома, а не один.** Репозитории не отнимут место у базы: PostgreSQL на заполненном диске может аварийно остановиться. Часть группы томов остаётся свободной — из этого запаса любой том растёт онлайн.
* **LVM внутри гостя, а не том гипервизора, проброшенный в ВМ.** Узел сам распоряжается своим местом, а диск данных лежит в пуле `vmpool` вместе с остальными дисками ВМ.

## Диск данных: том в пуле и подключение к ВМ

Команды раздела — на гипервизоре, из корня рабочей копии репозитория.

**Том в пуле.** Создаём его через пул libvirt, а не файлом в каталог пула: так учёт libvirt (`vol-list`, `vol-info`) всегда сходится с тем, что лежит на диске.

```bash
# Формат указываем явно: без --format том в dir-пуле создаётся raw,
# и описание диска с драйвером qcow2 такой файл не откроет
virsh vol-create-as --pool vmpool --name app-data.qcow2 --capacity 20G --format qcow2

virsh vol-info --pool vmpool app-data.qcow2
# Ожидаем: Capacity 20.00 GiB, Allocation — сотни KiB
```

Том тонкий: qcow2 занимает на хосте столько, сколько в него реально записано, поэтому запас размера почти ничего не стоит. Обратная сторона — обещанные размеры томов в сумме могут превысить реальный пул, так что свободное место пула стоит держать под наблюдением.

**Описание устройства** лежит в репозитории: [`configs/host/app-data-disk.xml`](../../configs/host/app-data-disk.xml). Оно собрано по образцу системного диска `vda` из постоянного описания ВМ (`virsh dumpxml --inactive app`) с тремя отличиями:

* `target dev='vdb'`, источник — новый том;
* `<serial>app-data</serial>` — по серийнику диск получает в госте стабильное имя `/dev/disk/by-id/virtio-app-data`. Имя `vdb` в описании — лишь подсказка: гость нумерует диски в порядке обнаружения;
* нет строки `<address>`: адрес `vda` занят, свободный PCI-адрес libvirt назначает сам.

**Подключение** — на лету к работающей ВМ, сразу в живое и в постоянное описание:

```bash
virsh attach-device app configs/host/app-data-disk.xml --persistent

virsh domblklist app
# Ожидаем: vda, vdb (app-data.qcow2) и sda — сид cloud-init

virsh dumpxml --inactive app | grep -B2 -A4 app-data.qcow2
# Ожидаем: блок <disk> нового диска с PCI-адресом, который назначил libvirt
```

Без `--persistent` диск проживёт только до первого полного выключения ВМ — например, до перезагрузки гипервизора. Поэтому постоянство проверяем по описанию с `--inactive`, а не перезагрузкой гостя: при `reboot` внутри ВМ процесс QEMU остаётся тем же, и устройство, подключённое только «вживую», никуда не денется.

Проверка на узле `app`:

```bash
lsblk
# Ожидаем: vdb 20G без разделов и точек монтирования

ls -l /dev/disk/by-id/ | grep app-data
# Ожидаем: virtio-app-data -> ../../vdb
```

## Тома LVM и файловые системы

Команды этого раздела и следующего — на узле `app`. Разметка разрушительна, поэтому сначала опознаём диск по серийнику и убеждаемся, что он пуст, а все команды адресуем по пути by-id — ошибка в букве диска не должна задеть системный `vda`:

```bash
readlink -f /dev/disk/by-id/virtio-app-data
# Ожидаем: /dev/vdb

lsblk -f /dev/vdb
# Ожидаем: колонка FSTYPE пуста — подписей файловых систем нет
```

Цепочка LVM: PV на весь диск → группа `vg_data` → тома `pgsql` (база) и `gitea` (репозитории):

```bash
sudo pvcreate /dev/disk/by-id/virtio-app-data
sudo vgcreate vg_data /dev/disk/by-id/virtio-app-data
sudo lvcreate -L 6G -n pgsql vg_data
sudo lvcreate -L 10G -n gitea vg_data

sudo pvs && sudo vgs && sudo lvs
# Ожидаем: PV /dev/vdb в vg_data, VFree около 4G, тома pgsql 6G и gitea 10G
```

* **PV на весь диск, без таблицы разделов.** Диск отдан только под данные: при нехватке места растим диск ВМ и выполняем `pvresize`, без промежуточного шага «растянуть раздел».
* **Размеры.** Репозиториям — 10 ГБ: в Gitea они растут быстрее базы, которая хранит метаданные. Базе — 6 ГБ. Около 4 ГБ остаются свободными в группе: из этого запаса любой том растёт онлайн, а забрать место у тома трудно — ext4 уменьшается только отмонтированной.

Файловые системы — ext4, как на гипервизоре: штатная и растёт онлайн.

```bash
sudo mkfs.ext4 /dev/vg_data/pgsql
sudo mkfs.ext4 /dev/vg_data/gitea
```

## Монтирование

Тома монтируются на уровень выше каталогов данных — в `/var/lib/postgresql` и `/var/lib/gitea`. В корне свежей ext4 лежит служебный `lost+found`, а утилита создания кластера PostgreSQL откажется работать в непустом каталоге; структуру `16/main` внутри пакет строит сам.

Монтирование поверх непустого каталога прячет его содержимое: файлы остаются «под» томом, их не видно, но место на корневом разделе они занимают. Поэтому точки монтирования создаём и проверяем пустыми:

```bash
sudo mkdir -p /var/lib/postgresql /var/lib/gitea
ls -la /var/lib/postgresql /var/lib/gitea
# Ожидаем: total 0 — каталоги пусты
```

Владелец корней томов пока root — хозяева появятся вместе со службами.

**fstab.** Узнаём UUID файловых систем и перед правкой системного файла сохраняем его копию:

```bash
sudo blkid /dev/vg_data/pgsql /dev/vg_data/gitea
sudo cp /etc/fstab /etc/fstab.bak
```

В конец `/etc/fstab` — две строки, каждая со своим UUID:

```text
UUID=<UUID тома pgsql>  /var/lib/postgresql  ext4  defaults,nofail  0 2
UUID=<UUID тома gitea>  /var/lib/gitea       ext4  defaults,nofail  0 2
```

* **UUID** — как у хранилища гипервизора (этап 1); переживает переименование тома или группы.
* **`nofail`** — без диска данных узел не уйдёт при загрузке в аварийный режим и останется доступен по SSH. Чтобы служба при этом не стартовала на пустом каталоге корневого раздела, её юнит должен зависеть от точки монтирования.
* **`0 2`** — `dump` не используется; `fsck` проверяет файловую систему при загрузке, после корневой.

**Проверка — от дешёвой к дорогой.** Ошибка, пойманная до перезагрузки, стоит минуту. Пойманная перезагрузкой — офлайн-правку диска ВМ: без сети в узел не попасть.

```bash
# systemd строит из fstab юниты монтирования — перечитываем
sudo systemctl daemon-reload

# Синтаксис, источники и точки монтирования — без монтирования
sudo findmnt --verify
# Ожидаем: Success, no errors or warnings detected

# Монтируем всё из fstab, что ещё не смонтировано
sudo mount -a

df -h /var/lib/postgresql /var/lib/gitea
# Ожидаем: /dev/mapper/vg_data-pgsql и /dev/mapper/vg_data-gitea
```

Последняя проверка — перезагрузка узла: fstab и активацию LVM выполняет загрузка гостя.

```bash
sudo reboot

# После загрузки
uptime -s
lsblk -f /dev/vdb
# Ожидаем: время загрузки — после настройки; vdb — LVM2_member,
# тома vg_data-pgsql и vg_data-gitea с ext4 смонтированы на свои места
```

## PostgreSQL

Ставим PostgreSQL 16 из штатного репозитория Ubuntu. Том `pgsql` к этому моменту смонтирован в `/var/lib/postgresql`, поэтому кластер, который пакет создаёт при установке, сразу ложится на него.

**Локаль — до установки.** Кодировку и локаль нового кластера `initdb` берёт из окружения, а SSH-клиент рабочей машины может передать на узел свои переменные локали (`LANG`, `LC_*`) — в том числе значения, которых на узле нет. Тогда пакет установится, но кластер не создастся или создастся не в UTF-8, а Gitea нужна база в UTF-8. Поэтому сначала:

```bash
locale
# Ожидаем: валидные значения (в образе — C.UTF-8) и ни одного предупреждения Cannot set LC_...
```

**Установка:**

```bash
sudo apt update
sudo apt install -y postgresql
```

Метапакет `postgresql` на Ubuntu 24.04 ставит версию 16. Пакет создаёт пользователя `postgres`, передаёт ему точку монтирования `/var/lib/postgresql` и создаёт кластер `16 main`. Обвязка Ubuntu (`postgresql-common`) раскладывает кластер так:

* конфиги — `/etc/postgresql/16/main/` (`postgresql.conf`, `pg_hba.conf`);
* данные — `/var/lib/postgresql/16/main/`, на томе;
* журнал сервера — `/var/log/postgresql/postgresql-16-main.log`: отдельным файлом, а не в journald.

Проверки:

```bash
pg_lsclusters
# Ожидаем: 16 main 5432 online, каталог данных /var/lib/postgresql/16/main

df -h /var/lib/postgresql/16/main
# Ожидаем: /dev/mapper/vg_data-pgsql

ls -ld /var/lib/postgresql /var/lib/postgresql/16/main
# Ожидаем: владелец postgres, у каталога данных права 0700
```

**Два юнита.** `postgresql.service` — зонтичный: сам ничего не запускает и после старта стоит в `active (exited)`, даже если сервер лежит. Настоящий сервер — экземпляр `postgresql@16-main.service`. Поэтому состояние базы проверяем по экземпляру и `pg_lsclusters`, а не по зелёному статусу зонтика.

```bash
systemctl is-active postgresql postgresql@16-main
# Ожидаем: active, active

systemctl show -p RequiresMountsFor postgresql@16-main
# Ожидаем: RequiresMountsFor=/etc/postgresql/16/main /var/lib/postgresql/16/main
```

Строка `RequiresMountsFor` замыкает схему с `nofail` из раздела «Монтирование»: юнит экземпляра получает `Requires=` и `After=` на монтирование тома. systemd смонтирует том до старта сервера и не запустит сервер, если монтирование не удалось: загрузка с `nofail` монтирования не ждёт, а сервер — ждёт.

**Где слушает сервер.** По умолчанию — только loopback (`listen_addresses = 'localhost'`). База нужна одному локальному приложению, поэтому настройку не трогаем:

```bash
sudo ss -tlnp | grep 5432
# Ожидаем: только 127.0.0.1:5432 — во внутреннюю сеть парка порт базы не смотрит
```

### Роль и база под Gitea

Права — минимальные: роль `gitea` может входить, но она не суперпользователь и не создаёт базы и роли — скомпрометированное приложение не выйдет за пределы своей базы. Владелец базы — та же роль: начиная с PostgreSQL 15 создавать таблицы в схеме `public` может только владелец базы, и база, созданная без `OWNER`, на первом старте Gitea ответит `permission denied for schema public`.

Пароль генерируем «скучный», из цифр и букв `a–f`: в `app.ini` Gitea символы `;` и `#` могут прочитаться как начало комментария, а в оболочке ломают команды `$` и кавычки.

```bash
openssl rand -hex 24
```

Роль и базу создаём от суперпользователя `postgres`. Ключ `-i` запускает psql в домашнем каталоге `postgres` — иначе psql предупредит, что не может перейти в каталог текущего пользователя:

```bash
sudo -i -u postgres psql
```

```sql
CREATE ROLE gitea WITH LOGIN;
\password gitea
CREATE DATABASE gitea WITH OWNER gitea ENCODING 'UTF8';
\q
```

Пароль задаём метакомандой `\password`, а не в SQL: psql превращает его в хэш SCRAM-SHA-256 на своей стороне, и открытый текст не попадает ни в историю psql, ни в журнал сервера.

Проверки:

```bash
sudo -u postgres psql -c '\l'
# Ожидаем: база gitea, владелец gitea, кодировка UTF8

sudo -u postgres psql -c '\du'
# Ожидаем: у роли gitea колонка Attributes пуста

psql -h 127.0.0.1 -U gitea -d gitea -c 'SELECT current_user, current_database();'
# Ожидаем: запрос пароля, затем gitea | gitea
```

### Вход в базу: кого и как пускает pg_hba.conf

`pg_hba.conf` — список правил: тип подключения (`local` — через Unix-сокет, `host` — по TCP), база, роль, адрес и метод. Сервер применяет первое совпавшее правило сверху; не совпало ни одно — отказ. Штатный файл Ubuntu разрешает то, что нужно Gitea, без правок:

* `host all all 127.0.0.1/32 scram-sha-256` — по TCP через loopback, с паролем. Так в базу будет ходить Gitea;
* `local all all peer` — через сокет, если имя пользователя ОС совпадает с именем роли. Поэтому `sudo -u postgres psql` входит без пароля. Для Gitea этот путь не годится: служба работает от пользователя `git`, а роль — `gitea`.

Метод входа для одной и той же роли зависит от того, как подключается клиент: `psql` без `-h` идёт в сокет. Так выглядит отказ:

```bash
psql -U gitea -d gitea
# FATAL:  Peer authentication failed for user "gitea"
```

Какое правило сработало, не гадаем по файлу — сервер пишет это в свой журнал:

```bash
sudo tail -n 10 /var/log/postgresql/postgresql-16-main.log
```

```text
LOG:  provided user name (gitea) and authenticated user name (devops) do not match
FATAL:  Peer authentication failed for user "gitea"
DETAIL:  Connection matched file "/etc/postgresql/16/main/pg_hba.conf" line 123: "local   all             all                                     peer"
```

Строка `DETAIL` с номером правила — первое, что стоит посмотреть, когда приложение «не пускают в базу».
